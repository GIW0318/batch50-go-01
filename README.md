# 令牌校验混淆探测

## 题面

客服复盘一起越权读取时发现，目标服务把签名算法被改成 none 的令牌放进了业务逻辑，而同一批探测里声明过期的令牌却被正常拒绝，前后结论对不上，取证材料也说不清到底缺的是哪一类校验。安全组要求把令牌校验的受控探测固化成可复用的流程，落点 gsb/batch50-go-safety-c-27，实现文件 jwt_confusion_prober.go，类型 JwtConfusionProber，签名固定：NewJwtConfusionProber(limits Limits) *JwtConfusionProber、Enumerate(sample Token) (Matrix, error)、Craft(caseID string) (Token, error)、Submit(caseID string, resp Response) error、Judge(caseID string) (Outcome, error)、Cleanup(caseID string) error、Snapshot() ([]byte, error)、Restore(data []byte) error，另配 Cases、Progress、CleanupAll、Close 四个辅助方法。

要修的点：一，样本缺少目标或算法就没有可比对的基线，直接拒绝；二，用例矩阵按固定顺序生成，先给 none、hs256、rs256 三种算法替换各一条，再按样本自带的声明顺序每个声明一条，最后一条空签名用例，编号由目标、类别、名称用斜杠拼成，算法用例形如 t1/alg/none，声明用例形如 t1/claim/exp，空签名用例固定为 t1/sig/empty，重复枚举同一目标必须得到完全相同的编号；三，单一目标的用例总数有上限，超出整批拒绝，不得留下半截矩阵；四，同一目标只允许一个批次在途，上一批用例没有清理完之前再枚举要拒绝；五，同时跟踪的目标数量封顶，关闭目标后名额才能复用；六，用例编号不存在时取令牌、回填响应、判定、清理都要报错，不能静默当成新用例；七，算法替换用例取出的令牌里，none 的签名段必须为空，hs256 与 rs256 必须带伪造签名，同一用例重复取令牌结果一致；八，有些目标把空签名当成合法，判定要看响应有没有真的进入受保护逻辑，只看状态码会把没进业务的情况算成命中；九，同一用例只接受一次响应回填，重复回填要拒绝，没有回填就判定要报错；十，判定结果必须给出是否命中、证据类型与未命中原因，签名替换与声明缺陷两类结论要分开给，不能互相替代；十一，清理要求单个用例已经判定，未判定的拒绝清理，重复清理同一用例仍然成功，批量清理允许带未判定用例并按作废处理、返回关闭条数，清理要把审计与缓存里的派生位置一并覆盖，不能只清内存里的用例；十二，进程重启后已回填与已判定的进度要保留，没有回填的令牌一律作废，再取令牌要报错。

硬约束：同一目标内用例串行推进，批次之间不共享令牌，不同目标之间互不阻塞；快照要么完整保存到已判定为止的进度，要么整体拒绝恢复，恢复后不得出现用例既作废又还能取令牌的中间态；单目标用例数、跟踪目标数与在途批次都有硬上限。

验收：go test ./... 的 15 条用例全过，测试不得修改、跳过或按固定输入写死；并发枚举与重启续跑自行验证；只做本地实现，交付源码、跑测记录与一页判定口径说明。
